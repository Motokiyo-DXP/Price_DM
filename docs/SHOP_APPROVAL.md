# 店舗候補の承認運用

チェーン店舗の一括登録と全件照合は `docs/SHOP_IMPORT_CHECKLIST.md` に従います。管理画面での直接登録は単店舗向けであり、チェーン全体の完全性確認には使用しません。

店舗候補を管理画面から確認・承認・却下・削除するための管理者向け手順です。公開画面や一般の `authenticated` ユーザーは、候補の閲覧や操作を実行できません。

## 前提

- 管理者のSupabase AuthユーザーIDを `private.admin_users` の許可リストへ登録済みである
- `/admin` にはMagic Linkでログインし、管理操作には価格登録用PINを使わない
- PIN、セッショントークン、Service Role key、SMTP認証情報をGit・Issue・スクリーンショットへ記録しない
- 最終構成では `shops` は承認済み店舗だけを保持し、未承認候補は `shop_candidates` に保持する

## 画面接続後の状態

価格登録画面は `search_shops_by_prefecture` の候補から承認済み店舗を選択します。店舗名に加え、任意の都道府県で候補を絞り込めます。`/api/price-records` は店舗IDを `shops` で再確認してから価格登録RPCを呼び出します。未登録店舗は `/api/shop-candidates` から候補として送信し、承認されるまで価格登録には使用できません。

価格登録APIは店舗IDを受け取る `submit_price_record_session_v3` を使用します。旧店舗名ベースRPCとその内部実装は `anon` / `authenticated` から実行できないため、アプリ外から未承認店舗を価格登録と同時に作成することもできません。

## 保留中候補を確認する

1. `/admin` を開く。未ログインの場合は `/admin/login` で許可済みメールアドレスへMagic Linkを送る。
2. 「店舗候補の確認」に表示される保留中候補を確認する。候補がなければ空状態が表示される。
3. 店舗名、住所、公式サイトを、候補に含まれるURL以外の経路でも確認する。

Supabase標準SMTPは送信レートが低いため、Magic Linkが届かない場合は連続送信しない。時間を空けて再試行し、恒常運用に移る場合だけカスタムSMTPを別途検討する。

ホーム画面の「管理者ページ」からも `/admin` を開ける。有効な管理者ログインセッションが端末に残っていれば認証画面を経由せず、期限切れ・未認証の場合だけ既存のMagic Linkログインへ移動する。

## 管理者が店舗を直接登録する

一般利用者からの候補申請を待たずに登録する場合は、`/admin` の「店舗を直接登録」を使用する。

1. 店舗名と都道府県を入力する。市区町村、住所、公式サイトURLも確認できる範囲で入力する。漢字を含む店舗名は「店舗名の読み」へひらがなまたはカタカナを入力する。
2. 略称、英字表記、通称などで検索される可能性がある場合は、「検索用の別名」へ1行に1件ずつ入力する。
3. 店舗公式サイトやTCG公式の取扱店一覧など、確認した根拠を「確認メモ」へ残す。
4. 「承認済み店舗として登録」を押す。
5. 完了メッセージを確認し、価格登録画面の店舗検索に表示されることを確認する。

この操作は管理者許可リストをRPC内で再確認する。画面上は直接登録だが、DBでは承認済みの候補監査レコードも同時に残す。同名の承認済み店舗がある場合や、同名の保留中候補がある場合は登録しない。保留中候補がある場合は候補一覧から内容を確認して承認または却下する。

## 既存店舗の情報を編集する

`/admin`の「登録済み店舗を編集」を使用する。店舗名・読み・登録済み別名・所在地で候補を絞り込み、対象店舗を選ぶ。絞り込みはひらがな・カタカナ、空白・中点・ハイフン、全角英字の表記差を許容する。

店舗名、所在地、公式URLは公式サイトや店舗SNSなどで確認した値を入力する。読みは確認できる店舗名の読みを入力する。別名は略称・英字表記・通称など、同じ店舗だと確認できた表記だけを1行に1件入力する。保存後は価格登録画面の店舗検索で想定した表記が一致することを確認する。

保存時には管理者許可リストをDB内で再確認する。変更前後の店舗情報と実行管理者は`private.shop_update_audit`へ保存され、公開APIからは参照できない。

## 誤登録した登録済み店舗を削除する

`/admin`の「登録済み店舗を編集」で対象店舗を選び、「登録済み店舗を削除」を押す。確認ダイアログの店舗名を確認してから実行する。

削除できるのは価格履歴が1件もない店舗だけである。価格履歴がある店舗は削除せず、店舗情報の修正を利用する。削除時にはDB内で管理者許可リストと価格履歴を再確認し、店舗情報・関連する候補情報・実行管理者を`private.shop_deletion_audit`へ保存する。関連候補は削除済み状態で履歴を残す。

## 承認する

候補の公式情報を確認できた場合だけ、管理画面の「承認」を選ぶ。確認内容はレビュー注記へ簡潔に残す。

承認後は、同一の承認済み店舗があれば再利用し、なければ `shops` に新しい店舗が作成される。候補は承認済みになり、以後の価格登録で候補店舗を選択できる。

## 却下する

既存店舗の表記違い、公式情報を確認できない場合などは、管理画面の「却下」を選ぶ。理由はレビュー注記へ残す。

## 誤登録した候補を削除する

誤操作で登録した保留中候補は「候補を削除」から削除する。確認ダイアログに表示された店舗名を確認してから実行する。この操作は保留中候補だけを対象とし、承認済み・却下済み候補、承認済み店舗、価格履歴は削除しない。

削除時もDB内で管理者許可リストと候補の状態を再確認する。削除前の候補内容と実行管理者は`private.shop_candidate_deletion_audit`へ保存され、公開APIからは参照できない。

## 店舗情報の修正依頼を処理する

1. 利用者は価格登録画面で承認済み店舗を選び、「選択した店舗の情報修正を依頼」を開く。
2. 変更したい項目だけと修正理由を入力して送信する。PINセッションが必要。
3. 管理者は `/admin` の「店舗情報修正依頼の確認」で現行値と提案値を比較する。
4. 内容を公式サイト等で確認し、承認または却下する。
5. 承認時だけ店舗マスターへ反映され、変更前後の値が非公開監査記録へ保存される。

同じ店舗に確認待ち依頼がある間は、新しい依頼を重ねて送信できません。修正依頼テーブルは公開APIから直接閲覧・更新できません。

## 操作後の確認

- 管理画面から候補が消え、保留中一覧に残っていないことを確認する。
- 承認した場合は、価格登録画面の店舗検索で承認済み店舗として選択できることを確認する。
- 管理画面に入れない、候補を二重処理しようとした、または候補の公式情報を確認できない場合は処理を止める。

承認・却下・削除RPCには管理者チェックがあり、公開APIロールに候補の閲覧・操作権限は付与されていない。権限変更後はSupabase Security Advisorも確認する。
