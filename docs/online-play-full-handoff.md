# オンライン対戦機能・全作業引き継ぎ

更新日: 2026-09-05

## 1. この文書の目的

本書は、TCG相場チェッカーへ追加中のオンライン対戦機能と、それに関連して同じ作業期間に実装・修正したカード操作、検索、アカウント、デッキ、買い物リスト等の状態を、別タスクから安全に再開できるよう記録するものです。

秘密鍵、PIN、アクセストークン、接続文字列などの認証情報は記載していません。

## 2. 現在の作業状態

- 作業ブランチは `codex/online-play`。
- 作業ツリーには、オンライン対戦機能を含む多数の未コミット変更・未追跡ファイルが存在する。
- 既存のユーザー変更を保持しており、整理、削除、reset、checkoutは行っていない。
- ローカルプレビューは通常 `http://192.168.1.15:3001` を使用してきた。
- ユーザーは、明示的に別方式を指定するまでローカルプレビューを希望している。ただし直近では、ローカルの全更新をVercel本番へ反映するよう依頼された。
- Vercel本番反映は未完了。詳細は「本番デプロイ」の節を参照。

## 3. オンライン対戦の確定要件

### 3.1 対戦方式

- 1対1。
- 観戦を許可。
- 公開ルーム、合言葉ルーム、フレンド招待を提供。
- 同一アカウントの複数端末接続を許可し、操作端末を1台に限定しない。
- 再ログイン時に以前参加していたルームを表示する。
- 両プレイヤー切断時は1分でルーム消滅。
- 片方切断時は5分で敗北確定。ただしルーム自体は直ちに削除せず、ルームへ戻った後、新規入室がさらに5分なければ削除。
- 通常の20分タイムアウトと切断タイムアウトは別扱い。

### 3.2 ルール管理

- 現段階ではゲームルールの自動判定を行わず、盤面同期と自由操作を中心にする。
- 不正操作をシステムが禁止しない。プレイヤー間で警告を送る機能を用意する。
- 勝敗の自動判定は行わない。
- リセットボタンの代わりに投了ボタンを置く。
- 基本的に敗者側の投了で勝敗決定。
- デフォルト制限時間は20分。通常タイムアウトでのみ引き分け。
- 制限時間、先攻・後攻はマッチ受付ごとに設定。先攻・後攻のデフォルトはランダム。

### 3.3 ルームとマッチ受付

- 最初のオンライン対戦ページには次の4選択肢を置く。
  1. ルームを作る
  2. 公開ルームへ参加
  3. 合言葉で参加
  4. 招待を受ける
- 作成ルームは4つのマッチ受付を持つ。
- 公開ルームは常設10枠で、誰でも参加可能。各公開ルームは10列のマッチ受付を持つ想定。
- ルールはルーム単位ではなくマッチ受付単位。
- マッチ受付でルール、使用デッキ、対戦者／観戦者を選択する。
- 対戦者2名だけが準備完了必須。観戦者の準備完了は不要。
- 両対戦者が準備完了した時点で、ホストの追加操作を待たず自動開始する。
- 準備完了までデッキを変更可能。準備完了時のデッキ内容を対戦専用コピーとして固定する。
- 公開ルームの設定変更時に準備完了状態は解除しない。
- 対戦開始後の途中参加は観戦者のみ許可。
- 対戦終了後は「再戦」「ルームへ戻る」を表示する。
- 再戦は両者同意が必要。手札・シールド・山札は再初期化し、それ以外の初期条件を維持する。
- 公開ルームの使用済みマッチ受付は対戦終了時点で解放・削除する。

### 3.4 同期対象

同期する盤面結果:

- 各ゾーンのカード
- カードの順番、重なり方、束構造
- 表向き／裏向き
- タップ／アンタップ
- マーカー
- ターンプレイヤーとターン番号

同期しない個人UI:

- 手札のスクロール位置
- Maya式操作パネル
- その他一時的UI状態

### 3.5 非公開情報

- 相手の手札は通常、枚数のみ表示。
- 山札の内容と順番はサーバーを正とし、両プレイヤーで同一状態を共有する。
- シールドは表向きだけ双方閲覧可能。裏向きは非公開。
- 「確認」は実行者だけ内容を見られるが、相手へリアルタイム通知する。
- 自分・相手どちらの非公開領域でも確認前に「本当に行いますか？ YES/NO」を表示。
- 裏向きの束はカード単位で公開状態を判定する。
- 観戦者は山札以外の非公開カードも閲覧可能。山札内容は観戦者にも非公開。
- 非公開情報は原則として相手クライアントへ不用意に送らない。確認等、明示操作が必要な場合は専用RPCで扱う。

### 3.6 操作権限と競合

- 両プレイヤーがお互いのカードを操作可能。
- ターン外操作を許可。
- 同じカードへの同時操作はターンプレイヤーを優先。
- サーバーを唯一の正しい状態とし、更新番号を持たせ、古い状態からの操作を拒否する。
- クライアントは競合時に最新盤面を再取得する。
- 対戦終了後は操作禁止。

### 3.7 通信方式

- Supabase Realtimeと盤面スナップショットを併用。
- 操作はサーバー検証後に確定し、Realtimeで他クライアントへ通知。
- 再接続時はサーバー側の最新盤面を取得し、更新番号を比較して復元。
- 同一操作の再送・重複適用を防ぐ。
- 通信中、再接続中、同期失敗をUI表示。

### 3.8 履歴と戻す／進む

- 現在ターンと1つ前のターンの操作履歴を保存。
- ターンエンド時に2つ前のターン履歴を削除。
- 自分が行った操作だけ戻せる。
- 自分が相手盤面を操作した場合も、自分の操作として承認なしで戻せる。
- 自分が行っていない操作は戻せない。
- ターンエンド取消のみ相手承認が必要。
- 対戦ログの後日閲覧は現時点で不要。将来リプレイを検討。

### 3.9 デッキ

- 対戦開始時に使用デッキをコピーして固定。
- 元デッキを対戦中に編集しても進行中対戦へ影響させない。
- 各カードにカードデータIDとは別の対戦内個体IDを付与。
- 禁止・制限カード検査は行わない。
- ルーム設定で許可されない外部ゾーンを持つデッキは選択不可。

### 3.10 シャッフルと公平性

- 山札シャッフルはサーバー側で実行。
- 結果は両者共通。
- ヨビニオン等、山札順を参照する処理もサーバー側へ委譲。
- クライアントから任意順序を直接確定できない構造を優先。

### 3.11 UI通知

- 相手が操作中のカードはプレイヤーカラーで発光し、アカウント名付きの「操作中」表示を追従させる想定。
- 自分のターン中に相手が行ったカード移動・シャッフルを通知。
- ターン変更、通信状態、確認要求を通知。
- 対戦通知はスクロールでは消さず、スクロール以外の操作完了時に消す。

## 4. 実装済みオンライン対戦機能

- オンライン対戦入口4選択肢。
- 作成ルーム、公開ルーム、合言葉参加、招待一覧のルートとUI。
- 公開ルーム常設枠とマッチ受付。
- ロビー内のマッチ受付とルームメンバー表示。
- フレンド招待ボタンと選択ポップアップ。
- ロビーで使用デッキを選択・変更し、デッキ編集画面を開く導線。
- 両対戦者準備完了で自動開始。
- 待機画面下への盤面埋め込みではなく、対戦専用ページへ遷移。
- Realtime接続状態表示。
- ロビー閲覧中または同じロビーで対戦中のメンバーだけを一覧表示。
- 公開マッチ終了時の受付解放。
- 対戦盤面のサーバー更新番号同期。
- 盤面保存の直列化と、待機変更の最新1件への集約。
- 再接続時の盤面再取得。
- サーバー権威シャッフル、ヨビニオン、確認、警告。
- 同時操作時のターンプレイヤー優先。
- ターン番号を「先攻1→後攻1→先攻2→後攻2」と共有する処理。

## 5. アカウントとプロフィール

- アカウント作成・管理画面でアカウント名とアイコンを設定可能。
- アカウント名は空白を除く1〜30文字。
- アイコンは設定時にルーム表示用128px相当へ圧縮。
- ルームメンバー一覧でアカウント名・アイコンを表示。
- マッチ受付へ入った対戦者のプラス記号をアイコンへ置換する設計。
- 共通ヘッダーの「管理」をGitHub型の `≡` アクションメニューへ変更。管理・フレンド追加等を表示し、最前面になるよう調整。

## 6. 盤面・Maya式操作の主な実装

### 6.1 Maya式操作パネル

- 長押し起動後、指を離さず選択肢へ移動し、pointerupで確定。
- 全Mayaパネルで上下境界を跨いでもフリーズしないよう、pointer lifecycleとrequestAnimationFrame更新へ統一。
- 端のカードから起動しても全選択肢が画面内に収まるよう中心点を補正。
- パネル外・中心領域でのキャンセル。
- 「その他」は指を離さず300ms保持すると同形式の第二層を表示。
- 第二層は1番空白、2カードの詳細、3タップ切り替え、4効果無視の疑い、5ヨビニオン、6マーキング。第一層と重複する項目は非表示。
- 長押し進捗を円形表示し、接触点の左上へ配置。

### 6.2 重ねる・束

- バトルゾーン内でカードAをカードBへ重ねられる。
- 重ね方パネルに「横・ずらして配置」を追加。
- 横ずらしは移動カードを対象の右側、Yずれなし、下階層へ配置。
- カードをドラッグし、別カード上で300ms経過後に円形進捗を表示、1000msで重ね方Mayaパネルを起動。
- 山札からドラッグしたカードでも同じ重ね方選択を利用可能。
- 束をドラッグすると束全体を移動。
- 束のMayaパネル4番に「束を開く」。
- 束を開いて下層カードをタップしても表示階層を変更しない。
- 束専用シャッフルEは全カードを裏向きにして順序をランダム化。
- 束専用反転Eは全裏なら全表、それ以外は全裏へ統一。
- 複数選択4番に「束にする」。

### 6.3 ドラッグ・スクロール・山札

- 全ゾーンの水平スクロール許容角度を±20度へ拡張。
- 一度ドラッグモードへ入った後は水平へ戻ってもスクロール判定へ戻さない。
- 山札へ移動する場合は「山札の上／下」ボタン上でpointerupした場合だけ確定。
- 山札を経由後、別ゾーンで離した場合は最終ゾーンへ移動。
- マナ・バトルゾーンから山札へドラッグしても上下選択UIを表示。
- ドラッグ中の移動先ゾーン／ボタンを `#8fffa1` で発光。
- 引用ゾーンが開いている場合、同一移動先のボタンとゾーンを両方発光。

### 6.4 表示・レイアウト

- 自分の引用ゾーン展開、相手盤面展開時に、増加UI実寸と固定手札の張り出しを最下部スクロール余白へ加算。
- 手札0枚表示はYを維持し、Xだけ画面中央へ固定。
- 初期表示時から手札を中央の扇形へ配置。
- 複数選択の発光は相手盤面省略状態に依存せず、カード輪郭へ追従。
- 複数選択中も中央カードを最上層に維持。
- 対戦デッキ名の左にあった「マイデッキへ戻る」を撤廃し、VS表示を中央配置。
- 相手ゾーンの赤枠欠損を4pxで補完。

### 6.5 その他カード操作

- マーキングをリセットで解除。
- マーキング効果ごとに＋／－を用意。
- 多色カードは公式文明配列に異なる文明が2種類以上含まれる場合だけ自動タップ。
- 山札以外のシャッフルにも共通の回転矢印アニメーション。
- 「確認」は自分側だけ表向き、相手側は裏向きのまま目印表示。別場所タップで解除。
- ヨビニオン通知タップで公開されたカードを確認可能。

## 7. ヨビニオン

確定仕様:

- 対象カードのコスト未満で、カード種類文字列に「クリーチャー」を含むカードを山札上から探索。
- 条件一致まで1枚ずつ仮置き場へ移動。
- 一致カードをバトルゾーンへ移動。
- 不一致カード群は全て裏向きの束にし、シャッフルして束ごと山札下へ戻す。
- ツインパクトや「タマシード/クリーチャー」も文字列包含で対象。
- オンラインでは非公開山札をクライアント検索せず、サーバーへ委譲。
- 「ヨビニオン・マルル」から「天災 デドダム」を呼べるよう、保存コスト欠損時の補完とDBメタデータ修復を実装。

## 8. デッキ・カード情報の関連実装

- デッキ編集画面のコスト順を数値コストで正しく昇順／降順ソート。不明・無限は末尾。
- 全並び替えに昇順／降順切替。
- 設定画面を開かなくても保存必須フィールドがFormDataへ残るよう修正。
- コスト、文明、カード種類を公式カードデータから取り込み。
- カード種類とコストのnull・不整合を監査・修復するスクリプトとマイグレーションを追加。
- デッキ固定コピーへカードメタデータを同期。
- 個体ID重複を避けて初期盤面生成。

## 9. カード検索とoriginal01読み

### 9.1 検索仕様

- デッキ編集、相場一覧、価格登録など全カード検索が共通DB関数 `public.search_canonical_cards` を使用。
- 英字、ひらがな、カタカナ、漢字以外の文字・記号を無視して検索。
- 例: `GOD` で `極まる侵略 G.O.D` 等を検索可能。
- 公式にない特殊ルビは、既存データとは別の検索語として `source = 'original01'` で保持。
- 既存データまたはoriginal01のどちらかに一致すれば検索結果へ表示。

### 9.2 original01取得・反映状況

- ユーザーはデータ利用許可を取得済みと説明している。
- 取得済み1,189種類。
- 読みを抽出できた853種類。
- Supabaseへ反映済み検索語1,346件。空検索語0。
- `ゼットラッシュ` で `“絶闘乱襲”ブランド` が返ることを確認。
- 全対象は約11,687種類で、残りは未取得。
- 継続取得スクリプト `scripts/fetch-dmwiki-original01.mjs` は再開時にNode.jsからHTTP 403となり2回安全停止。
- 同時点でPowerShellからrobots.txtはHTTP 200だったが、自動取得制限を回避する変更は行っていない。
- 現在バックグラウンド取得プロセスは動いていない。

### 9.3 検索性能

確認済み根本原因:

- 旧検索関数が約11,687件の各カードごとに `card_search_terms` と `card_prints` をLATERAL集計していた。
- 基本インデックス不足ではなく、カード単位の反復クエリ形状が主因。

修正:

- 検索語と収録版をそれぞれ一度走査・集約し、候補カードだけ収録数を数える構造へ変更。
- 固定デバウンスを250msから共通50msへ短縮。

計測:

- DB実行時間: 約1,527ms → 約182ms（約88.1%短縮）。
- REST中央値: 約292ms。
- デバウンス込み推定表示開始: 約1,887ms → 約342ms（約81.9%短縮）。
- `GOD`、`ゼットラッシュ`、`天災` の変更前後結果一致を確認。

## 10. 相場・買い物リスト

- 星によるローカル絞り込みを廃止し、アカウント単位のDBブックマークへ移行。
- 相場一覧の同じ位置に添付カートSVGを使った買い物リスト導線。
- 買い物リストは販売／買取切替。デフォルト販売。
- ブックマークカードを店舗ごとの最安・次点へ分類。
- 最安値と平均価格を表示。
- カードボックス全体タップで詳細へ遷移し、独立した「詳細」リンクは廃止。
- スマホは買い物リスト導線をアイコンのみ表示。
- 買い物リスト背景、カード画像比率、店舗名サイズ、スマホ縮尺を調整。
- 相場一覧カードにもカード画像を表示。
- ログイン済みユーザーは価格登録PINを免除。

## 11. Supabase・DB構成

主要テーブル／領域:

- `canonical_cards`: 正規カード、コスト、文明、カード種類等。
- `card_prints`: 収録版、画像キー、商品名、カード番号。
- `card_search_terms`: 表示名、読み、別名、original01読み等の検索語。
- `decks`, `deck_cards`, `deck_folders`: ユーザーデッキ。
- `account_profiles`: アカウント名、圧縮プロフィールアイコン。
- `account_card_bookmarks`: アカウント単位ブックマーク。
- `online_lobbies`, `online_lobby_members`, `online_lobby_invitations`: ロビー、参加者、招待。
- 公開ルーム／マッチ受付関連テーブル。
- `game_rooms`: 対戦状態、参加者、勝敗、切断・保持期限等。
- ゲーム盤面スナップショット、操作履歴、presence、spectator、undo関連テーブル。

セキュリティ判断:

- 公開スキーマのテーブルはRLS前提。
- 非公開盤面・山札操作は専用RPC経由。
- `SECURITY DEFINER` を安易な権限回避に使用しない。
- 必要な関数は実行権限を明示し、PUBLIC既定権限に依存しない。
- クライアントへservice role等の秘密鍵を置かない。

## 13. 重要RPC・処理契約

- 公開マッチ終了時、受付を解放。

## 15. これまで発生した主な不具合と確認済み原因

### 15.1 Mayaパネル境界フリーズ

症状: 指を離さず上下半分を往復すると水平境界付近でフリーズ。

確認事項: 開いているMayaパネルより先にゾーンの水平スクロール判定が介入し、pointer更新経路が途切れていた。パネルpointer lifecycleを優先し、更新をrequestAnimationFrameへ制限して修正。

### 15.2 ドラッグ後に水平移動で解除

確認事項: ドラッグ成立後も初期の角度分類が再評価されていた。ドラッグを不可逆な状態遷移にして修正。

### 15.3 手札と追加UIの重なり

確認事項: デフォルト固定余白だけで、引用ゾーン等の実寸と固定手札の上方向張り出しが反映されていなかった。実寸測定値を最下部余白へ加算。

### 15.4 デッキのコスト順

確認事項: コスト欠損と表示文字列、カードグループ単位の並びが混在していた。公式コストを数値化し、不明値を末尾へ置く共通ソートへ変更。

### 15.5 準備完了後に対戦ページへ移動しない

確認事項: 自動開始後も待機ページ内の状態表示へ留まり、専用battle routeへの遷移条件が接続されていなかった。開始状態検出後に専用ページへ遷移。

### 15.6 準備完了取消で入口へ戻る

確認事項: 取消送信時に選択中デッキIDが欠落し、参加状態が解除扱いになっていた。選択済みデッキIDを維持して準備状態だけ更新。

### 15.7 ルームメンバーが残り続ける

確認事項: membershipと現在presenceが区別されていなかった。有効presenceまたは同ロビー対戦中で絞り込み。

### 15.8 検索ラグ

確認事項: 全カードに対するLATERAL反復集計が主因。インデックスの推測修正ではなく、実行計画と実測から一括候補抽出へ変更。

### 15.9 買い物リストで価格未登録表示

確認事項: 正規カードID・収録版IDの価格結合経路差と、店舗表に存在しない列参照が関係。カード共通価格優先、収録版fallback、実在列だけを取得するよう修正。

### 15.10 ローカルNext.jsのvendor-chunksエラー

確認事項: devとbuildが同じ `.next` を同時利用すると生成物が壊れることがある。dev稼働中に `npm run build` を並行実行しない。

## 16. 試行して失敗・中断した対応

### 16.1 original01継続取得

- Node.jsスクリプトをバックグラウンド起動したがHTTP 403で停止。
- robots.txt単体はPowerShellで200だった。
- TLS指紋やUser-Agent変更による回避は行っていない。
- 取得元が許可するAPI／取得方法を確認してから再開する。

### 16.2 Vercel本番反映

- `vercel deploy --prod` は未コミット変更が大量にあるため安全審査で拒否。
- 初回送信では23,469ファイルとなりVercelの15,000件上限超過。
- `--archive=tgz` を試したが、`public/cards/official` の除外パターンが末尾スラッシュ付きで効かず、約1.2GB送信しようとしたため中断。
- `.vercelignore` を作成し、現在は `public/cards/official` を末尾スラッシュなしで除外。
- 添付資料、ローカル取得物、制作素材、生成物、テスト等も除外。
- その後も未コミット状態の外部送信リスクを理由にproduction／previewとも安全審査で拒否。
- 本番URLは更新されていない。

## 19. 再開時の注意点

- 最初に `AGENTS.md` を読む。
- バグ修正は再現、関連コード調査、根本原因特定、最小修正、実画面確認、テストの順で行う。
- 以前の修正が失敗している場合はgit diff/historyを調べ、CSSオフセットやdelay等の回避策を重ねない。
- 作業ツリーはdirty。ユーザー変更を上書き・削除しない。
- `apply_patch` を優先。Windows sandbox helperが失敗した場合だけ、対象を限定したPowerShell置換を使い、その旨をユーザーへ伝える。
- devサーバー稼働中に`npm run build`を実行しない。
- Supabase変更時は最新ドキュメント、RLS、関数権限、advisors、実クエリを確認。
- DDLは正式migrationを作成し、適用後にmigration一覧と結果を確認。
- Vercel送信前に `.vercelignore` が効くこと、送信ファイル数・容量が小さいことを確認。
- 本番反映は、未コミット多数・外部送信・不整合リスクを説明した後の、ユーザーによる新しい明示承認が必要。
- 安全な流れは隔離preview作成→ビルド・主要ルート・ログ検証→同一成果物をpromote。
- 大容量送信が再発したら即停止し、ディレクトリを削除・移動して回避しない。
- original01の403をUser-Agent偽装等で回避しない。許可された取得方式を確認する。
