## 原因

1. `public.normalize_card_search` は現行仕様として長音も除去する。「ゲート」は「げと」(2文字)になる。正規化そのものは変更していない。
2. `20260924185334_deck_market_search_first_response.sql` の `public.search_market_cards` は `char_length(normalized_query) between 1 and 2` を短文経路の条件にしており、部分一致・trigramを実行しない。デッキ編集の `private.search_deck_card_term_matches` も同じ判定だった。
3. 登録画面の `20260923145858_optimize_registration_long_search.sql` / `private.search_registration_cards_long` は入力3文字なので長文経路へ進むが、部分一致・trigramの条件 `char_length($1) >= 3` が正規化済み文字列を参照し、同じ結果になる。
4. RPCの部分一致条件自体は残っていたが、この語では到達できなかった。単なるデータ未登録ではなく、専用テストDBに登録した「ヘブンズ・ゲート」でも再現した。
5. 各RPCは検索語全体を正規化していたため、複数語が連結され、逆順の「ゲート ヘブンズ」は一致しなかった。フロントの検索依存キーも空白を消していた。
6. 登録候補30件・相場100件には続きの取得経路がなかった。デッキ編集には既存のoffset/スクロール追加取得がある。相場のRPC結果に対するクライアント側の再フィルターはなく、主原因ではなかった。
7. 旧 `search_canonical_cards` は単語検索で短文にも部分一致する別仕様だった。現在の主要3画面はこのRPCを直接使わない。旧APIの単語検索は維持し、複数語のみAND検索へ対応した。公開デッキ一覧のデッキ自体の検索処理は変更していない。

## 検索仕様

空白分割を先に行い、各語を現行の `normalize_card_search` で正規化する。検索方式の判定だけは長音を残した入力文字数を使う。各語の1〜2文字は前方一致、3文字以上は前方一致・部分一致・既存閾値のtrigram。登録済みの読み・別名・face名を維持し、収録番号・商品名も既存経路を保持する。

複数語は同じcanonical IDで全語の候補が揃うAND検索。異なる検索対象項目に分かれた一致も可能。空白・全角空白・連続空白・語順反転に対応。候補を途中で打ち切らず、ゲーム・有効性・既存属性で絞ってから順位付けとページ取得を行う。

順位は完全一致、前方一致、部分一致、trigramを基本に維持。相場・デッキのofficial/face名とalias/読みのprefix優先度、登録画面の短文の既存スコア、デッキの指定ソートを維持。同順位はIDも使いページ境界を安定させる。

テーブル・データ・正規化済み語・索引の追加や一括更新は行わない。RLS変更なし。新しい検索ヘルパー・ページRPCはSECURITY INVOKER。既存デッキ内部関数のSECURITY DEFINERとauth.uidチェック、既存公開RPCの実行ACLは維持し、SQLテストで比較済み。
